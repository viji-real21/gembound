Abstract

AI coding agents burn money in predictable ways: they start work they should have refused, restart from scratch instead of staying warm, let context grow without bound, spawn copies of themselves, and work at the most expensive hour. We built a workflow — a set of ordering and scheduling rules around one agent session — where each of these waste mechanisms is either prevented before any model call happens or bounded by arithmetic on the provider's own published prices. Every claim below is one of: PROVEN (exact math, CI-enforced), MEASURED (data from this machine), or NOT YET MEASURED (stated honestly, experiment pending). No number on this page is a projection dressed up as a result.

What the workflow is (no LangGraph knowledge needed)

Think of a factory gate. Orders arrive; some should be rejected at the gate (budget spent, work-in-progress full) before anyone expensive touches them. The workflow is five such rules, plus a scheduler:

  1. Guards before model work. Usage and work-in-progress checks run before the first model call, not after. A refused order costs 0 tokens.
  2. One warm session. Work continues in a session whose conversation history is cached, instead of a fresh session per task.
  3. Bounded context. The conversation is summarized past a fixed size (~80–100k tokens), so per-turn cost never grows without bound.
  4. No cloning. On a credit-capped plan, the session never spawns parallel sub-agents.
  5. Off-peak scheduling. Heavy batch work runs when the provider bills 50%.

A "shadow" implementation of the same decision logic was built as an explicit graph (LangGraph) and replayed against 12 recorded scenarios — same prices, same outcomes, only the order of checks changed. That replay is where the guard numbers come from.

The five proofs, in plain language

1. Guards can only remove work, never add it

A guard is a check that costs 0 model tokens and only routes. Deleting a guard cannot remove model calls — it can only unblock more of them. So for every possible input: guarded ≤ unguarded, strict whenever a guard fires. We did not just argue this — we fired 2,750 randomized states (plus a 2,000-state adversarial sweep) covering every budget level, work-in-progress level, context size and mode: 0 violations. A refused state never burned a single token. Raising any budget pressure never increased started work.

2. The saving is exact on recorded scenarios

12 recorded scenarios, identical prices both sides: the unguarded order pays 444,000 tokens, the guarded order 396,000. The 48,000 difference is exactly four 12,000-token planning calls that guards cancelled before they happened — nothing else differs. Per scenario the saving is either 0 or exactly 12,000, so the interval [0%, 10.81%] is tight at both ends: it cannot be beaten up, and it cannot be squeezed.

3. Warmth is a 2.79× multiplier

The provider prices a token of context at 6.9 units when fresh but 1.7 when cached, and output at 24. For a typical 90k-token turn with 90% cache hit and 1.5k output, arithmetic gives 11.8 credits warm vs 32.9 fresh — the same task, 64% cheaper, i.e. 2.79× more work per credit. This is why the workflow's rule is "one warm session, never restart cold."

4. Unbounded context is quadratic; bounded is linear

If context grows by g tokens per turn, turn t costs at least proportional to t·g, and T turns cost Θ(T²). Summarizing past a fixed window W bounds every turn's cost, making T turns cost O(T). Boring calculus, decisive money: without the rule the bill accelerates; with it, it's a straight line.

5. Cloning yourself is provably wasteful on a credit plan

A sub-agent starts with a fresh, uncached context (≥23,000 tokens measured on this fleet — about 7.9 credits each before doing anything). Credits don't care about wall-clock, so k clones cost ≥7.9k credits where continuing in-session costs one cached turn (~11.8). Parallelism buys speed on time-metered subscriptions; on a credit-capped plan it buys only expenditure. Hence: no fan-out on the backup lane.

The rule we run: on time-metered subscriptions, fan out only for independent review and work ≥ 30k tokens (parallelism + independence pay for the fresh contexts); on the credit-capped backup lane, never fan out — same roles, one session, CI tests act as the critic.

What this does NOT prove (read this part)

The honest gap. The 10.81% guard saving is an exact upper bound on recorded scenarios. In live operation the existing shell hooks may already catch some of those calls, so the realized live saving sits somewhere in [0%, 10.81%] — one pending experiment (a capped live canary) pins it. Speed/cycle-time is not yet measured. Results use one provider's published prices (z.ai GLM Coding Pro); constants like the 2.79× warmth multiplier depend on that price sheet, while the structure of every proof (guards-only-remove-work, monotonicity, cache arithmetic, linear-vs-quadratic) holds for any provider that prices cache cheaper than fresh context. Anyone selling this as "mathematically proven 10.8% savings, guaranteed" is misrepresenting page 1.

Why a third lane exists at all

The workflow runs on two metered subscriptions. When both hit their weekly caps, a $20 credit-capped backup lane (the same rules, minus everything that spawns processes) keeps the system alive: measured burn for a heavy half-day was 1,031 of 12,000 rolling-window credits (8.6%) and 1.9% of the weekly 60,000 — with a soft-stop at 40,000 that fires long before exhaustion. The nightly planner, which failed two nights running on capped subscriptions, has run clean since moving to this lane.
